# 공간 운영 릴리스 검증 런북

이 문서는 운영자가 공간을 만들고, 여러 참여자가 참여해 편지를 예약·수신·읽는
핵심 여정을 릴리스 후보마다 반복하는 절차다. 전체 화면 E2E가 아니라 공간 도메인의
출시 차단 기준과 실제 기기 확인을 한 곳에 모은다.

## 1. 출시 차단 기준

아래 항목은 하나라도 실패하면 릴리스 후보를 배포하지 않는다.

- 운영자 1명과 참여자 2명 이상이 같은 공간·회차·슬롯을 확인한다.
- 가입/참여 신청/승인/시작/예약이 각 역할의 권한으로만 성공한다. 비참여자는
  공간 글·예약·수신함을 볼 수 없다.
- 예약은 KST 06:00으로 저장되고, 회차의 슬롯 날짜 밖으로 저장되지 않는다.
- 발송 전에는 수신함에 나타나지 않으며, 발송 후에는 발송 대상자에게 정확히 한 번만
  나타난다. 같은 스케줄러 실행을 두 번 해도 슬롯·회차·수신 결과 수가 변하지 않는다.
- 앱 재시작과 네트워크 단절 후 복구 시 예약/읽기 상태가 중복되거나 사라지지 않는다.
- 익명 공간의 모집 중 화면과 수신함에서 실명, 계정 닉네임, 이메일, 원문 토큰이
  노출되지 않고 필요한 경우 표시명은 `참여자`다.
- 웹, iOS, Android에서 동일한 공간 ID, 회차 번호, 슬롯 날짜, 예약 상태, 수신함
  결과를 확인한다.
- 자동화 검사, 기기 확인, 데이터 정리, 진단정보 수집이 모두 기록된다.

## 2. 격리된 검증 데이터

### 실행 전 고정

1. 릴리스 후보의 `release.track`, 앱 버전/빌드 번호, API 호스트, DB 스키마
   버전을 기록한다. URL 전체나 비밀값은 기록하지 않는다.
2. 운영 DB와 분리된 staging Supabase 프로젝트/스키마를 사용한다. staging을
   제공할 수 없으면 테스트 계정과 공간 이름에 `release-check-<UTC 날짜>-<실행 ID>`
   접두사를 붙이고 운영 공간을 선택하지 않는다.
3. 다음 테스트 계정을 준비한다.
   - `operator`: 공간 생성·승인 권한을 가진 계정
   - `participant-a`, `participant-b`: 서로 다른 참여자 계정
   - `outsider`: 공간에 승인되지 않은 계정
4. 이메일, 실명, 실제 닉네임, 실제 편지 내용은 사용하지 않는다. 테스트 본문에는
   실행 ID만 넣는다.

### 실행 후 정리

- 테스트 계정의 세션을 로그아웃하고, 테스트 공간을 `ARCHIVED`로 종료한다.
- 테스트 공간의 예약, 회차, 슬롯, 공간 편지, 수신함 결과를 실행 ID로 조회해
  확인한 뒤 staging에서만 삭제한다.
- 삭제 전에는 결과 개수와 실패 원인을 기록하고, 운영 DB에서는 절대 광범위한
  `DELETE`를 실행하지 않는다.
- 정리 실패는 성공으로 간주하지 않는다. 공간 ID, 실행 ID, 실패 단계만 남기고
  차단 상태로 운영 담당자에게 전달한다.

## 3. 자동 검증

저장소 루트에서 실행한다.

```bash
pnpm verify:space-release
```

이 명령은 데이터를 변경하지 않고 다음 검사를 실행한다.

| 검사 | 포함 범위 | 차단하는 문제 |
| --- | --- | --- |
| API 공간 여정 계약 | 참여 신청/승인, 역할별 예약 조회, 공개/수신자 전용 글, 발송 트랜잭션 | 권한 우회, 슬롯 변경 후 잘못된 발송, 중복 수신, 부분 실패 후 가짜 `SENT` |
| 클라이언트 날짜·표시 계약 | KST 날짜 경계, 참여 검증, 회차 상태, 예약 재시도 정책 | 기기 시간대에 따른 날짜 이동, 잘못된 예약 가능 상태, 중복 예약 UX |
| 릴리스 발행 가드 | preview/production 공개 설정 누락 | 설정이 비어 있거나 다른 API/DB를 가리킨 채 빌드·제출 |

실행 결과는 `/tmp/space-release-verification-<timestamp>.json`에 저장된다. 보고서에는
검사명, 합격/차단, 소요 시간, 종료 코드만 남기며 테스트 내용·토큰·이메일은 넣지 않는다.
실제 배포 API와 DB readiness까지 확인하려면 staging 또는 출시 후보 API의 호스트만
환경변수로 주고 실행한다.

```bash
SPACE_RELEASE_API_URL=https://<staging-api-host> \
  pnpm verify:space-release -- --live --report /tmp/space-release-live.json
```

`--live`는 `/api/healthz`와 `/api/readyz`만 호출한다. `/readyz`가 성공해야 API가
실제 DB에 연결된 것으로 보며, 이것만으로 역할 여정 합격을 선언하지 않는다. 요청은
인증·쓰기 없는 읽기 전용 확인이다.

## 4. 역할별 운영 리허설

아래 순서를 같은 `runId`로 기록한다. 각 단계의 화면 캡처에는 이메일, 토큰, 원문
편지를 포함하지 않는다.

| 단계 | 실행 역할 | 실행 | 기대 결과 | 차단 기준 |
| --- | --- | --- | --- | --- |
| A1 | operator | 새 계정으로 로그인 후 공간 생성 | 모집 중 공간과 1회차가 생성되고 운영자 역할이 보인다 | 공간 ID가 없거나 다른 사용자가 운영자로 표시됨 |
| A2 | participant-a/b | 초대 또는 초대 코드로 참여 신청 | 각 계정의 신청이 대기 상태로 분리됨 | 서로의 신청이 섞이거나 비참여자가 신청 성공 |
| A3 | operator | 두 신청을 승인하고 공간 시작 | 동일한 회차 ID와 슬롯 순서가 전 기기에서 보임 | 승인 전 노출, 슬롯 중복, 회차 번호 불일치 |
| A4 | participant-a | 내 중심글 슬롯에 편지를 예약 | 내 슬롯 날짜만 선택 가능하고 발송 시각은 KST 06:00 | 다른 사람 슬롯 선택 가능, 로컬 시간 저장 |
| A5 | participant-a | 같은 예약 버튼을 빠르게 두 번 누름 | 하나의 예약만 남고 중복 안내가 표시됨 | 예약 2개, 슬롯 이동, 무한 로딩 |
| A6 | operator | 여는 편지를 예약하고 예약 목록 확인 | 운영자에게 본인 예약만 보이고 예약 상태가 유지됨 | 참여자 예약이 운영자 목록에 섞임 |
| A7 | scheduler/operator | 예약 시각 전후에 발송 처리 실행 | 전에는 미노출, 후에는 대상 수신함에 한 건 표시 | 조기 노출, 작성자 자기 수신, 누락/중복 |
| A8 | participant-a/b | 수신함에서 열고 끝까지 읽기 | 읽음 상태와 읽기 기록이 유지되고 같은 글 중복이 정리됨 | 읽음 되돌림, 다른 회차 글 표시 |
| A9 | outsider | 공간 상세·글·예약·수신함 접근 시도 | 401/403 또는 빈 결과 | 공간 내부 글·예약·멤버 정보 노출 |
| A10 | operator | 공간 종료 후 재조회 | 종료 공간은 새 예약이 막히고 과거 발송 기록만 보존됨 | 종료 후 예약 생성, 과거 `SENT` 기록 훼손 |

## 5. 시간·재시도 경계

검증용 예약 3개를 만든다. 실제 운영 시간에 영향을 주지 않도록 staging에서
실행하고, 기준 시각은 항상 KST로 기록한다.

1. `T-1분`: 예약이 수신함에 나타나지 않는지 확인한다.
2. 정확히 `06:00 KST`: 스케줄러를 두 번 연속 실행한다. 첫 실행만 `PENDING → SENT`가
   되고, 두 번째 실행은 수신함 행을 추가하지 않아야 한다.
3. `T+1분`: 운영자·참여자별 수신 결과를 비교하고, `visibleAt`과 `scheduledAt`이
   같은 예약 인스턴스를 가리키는지 확인한다.
4. 발송 트랜잭션 중 수신함 삽입이 실패한 상황을 재현한다. 상태는 `PENDING`에
   남아 재시도 가능해야 하며, 부분 수신 후 `SENT`로 조기 전환되면 안 된다.
5. 발송 직후 앱을 강제 종료하고 재실행한다. 예약·회차·수신함 결과가 서버 결과와
   같아야 한다.
6. 오프라인에서 예약 버튼을 누르고 온라인으로 복귀한다. 재연결 전에는 성공
   화면으로 확정하지 않고, 복귀 후 한 번만 서버 결과를 반영해야 한다.

## 6. 익명 공간 개인정보 점검

익명 공간에서는 다음 계정 조합을 각각 확인한다.

- 모집 중인 `operator`, `participant-a`, `outsider`가 보는 참여자 이름은 `참여자`
  또는 정책상 허용된 공간 닉네임뿐이다.
- 수신함의 `sender` 객체에 계정 닉네임·이메일이 포함되지 않는다. 표시용
  `senderDisplayName`만 사용한다.
- 발송된 편지의 작성자와 수신자 교차 조회에서도 실명/계정 닉네임을 추정할 수
  있는 필드가 없어야 한다.
- 로그, 진단 번호, 화면 오류 문구에 이메일, bearer token, anon key, 응답 본문,
  원문 예외가 없어야 한다.

## 8. 증거와 실패 분류

### 남길 안전한 증거

- `runId`, 실행 UTC 시각, 테스트 DB 환경명
- 앱 버전/build, `release.track`, API 호스트명, 설정 지문
- 공간/회차/예약/수신함의 개수와 상태, 필요한 경우 짧은 내부 ID
- 플랫폼·OS 버전·네트워크 전환 단계
- 자동 검사 보고서 경로와 실패한 검사명
- 가입/동기화 진단의 오류 종류와 `flowId`/진단 번호

### 남기지 않을 값

이메일, 실명, 실제 닉네임, 편지 원문, access/bearer token, Supabase anon key,
쿼리 문자열, 응답 본문, 원문 예외 메시지, 전체 URL.

### 실패 분류

| 분류 | 예시 | 1차 대응 |
| --- | --- | --- |
| `CONFIG` | 설정 누락/지문 불일치, 잘못된 track | 빌드·제출 중지 후 해당 EAS 환경 수정 |
| `AUTH` | 새 설치 로그인, 세션 복구 실패 | 앱 설정/인증 도달 여부 확인, 진단 번호로 흐름 조회 |
| `ACCESS` | 비참여자 노출, 익명 정보 노출 | 즉시 차단, 영향 범위와 응답 필드 확인 |
| `SCHEDULE` | KST 경계·슬롯 날짜 불일치 | 예약/회차/서버 시간대와 저장 instant 대조 |
| `DELIVERY` | 누락·중복·조기 노출 | reservation ID 기준으로 발송·수신함 원자성 확인 |
| `RECOVERY` | 재시작·오프라인 복구 후 상태 변형 | 마지막 서버 상태와 재시도 요청의 중복 여부 확인 |
| `PLATFORM` | 한 플랫폼만 레이아웃·딥링크·푸시 실패 | 해당 빌드 번호/OS/로그를 붙여 릴리스 차단 |

차단된 경우 담당자는 `runId`, 단계, 플랫폼, 기대/실제 상태, 재현 시각(KST),
안전한 진단 번호만 전달한다. 원문 로그나 계정 정보를 첨부하지 않는다. 모든 차단
항목이 재현 없이 수정되고 자동 검사와 해당 플랫폼 재검증이 통과한 뒤에만
`GO`로 판정한다.
