# 읽는 중 메모 방향 검토

> 상태: 제품 방향 결정을 위한 근거 문서  
> 범위: 현재 동작과 코드 구조 분석, 세 가지 방향 비교, 결정에 필요한 측정·검증 제안  
> 비범위: 방향 확정, UI/API 변경, 데이터 삭제·마이그레이션 실행

## 1. 요약

현재 읽기 화면에서 사용자가 보는 “메모”는 별도 메모 문서가 아니다. 실제 저장 단위는 기존 **단상(Thought)** 이며, 원본 글과 연결된 `PRELIMINARY` 단상으로 저장된 뒤 공용 작성 화면에서 계속 편집된다.

- 읽기 화면의 FAB와 위로 스와이프는 글에 연결된 `ThoughtsBottomSheet`를 연다.
- 문장 선택 후 “메모”를 누르면 인용문을 단상 시트 입력창에 채우지만, 아직 저장하지는 않는다.
- 입력을 전송하면 `createdFrom: "reading"`, `sourceArticleId: 현재 글`, `status: "PRELIMINARY"`인 단상을 만들고 공용 작성 화면(`/on-01a`)으로 이동한다.
- 시트에 보이는 기존 항목도 같은 글에 연결된 단상이며, 편집을 누르면 공용 작성 화면으로 이동한다.
- 읽기 완료 질문 답변은 완료 커밋 직전에 답변 하나당 `createdFrom: "question"` 단상을 별도로 만든다.
- 과거 메모 전용 편집·페이지 전환 구현은 코드에 남아 있지만 현재 읽기 화면에서는 가져오거나 렌더링하지 않는다.

따라서 지금의 제품 계약은 **“읽는 중 메모”라는 진입 언어로, 글에 연결된 단상을 빠르게 시작한다**에 가깝다. 반면 코드와 이벤트에는 “메모 문서”, “단상”, “질문 답변”의 세 개념이 섞여 있다.

현재 분석만으로는 세 방향 중 하나를 확정할 수 없다. 특히 “열기 → 실제 저장 → 다시 열람 → 글로 발전”의 전환과 저장 실패율을 측정하지 않고는 현행 유지, 저널 확장, 진입점 종료 중 어느 쪽이 더 큰 사용자 가치를 만드는지 판단하기 어렵다.

**조건부 권고:** 먼저 2~4주 동안 최소 퍼널과 저장 신뢰성을 측정한다. 그동안은 대규모 저널 재설계를 시작하거나 기존 코드를 삭제하지 않는다. 측정 결과가 나오기 전 기본 선택지는 비용과 가역성이 가장 낮은 **① 현행 단상 흐름 유지·개선**으로 둔다.

## 2. 현재 사용자 흐름과 저장 계약

### 2.1 한눈에 보는 흐름

```text
[읽기 페이지]
   ├─ FAB 탭
   │    └─ 단상 시트 열림
   │         ├─ 새 단상 입력·전송
   │         │    ├─ Thought 생성
   │         │    └─ 공용 작성 화면(/on-01a)으로 이동
   │         ├─ 기존 단상 선택
   │         │    └─ 공용 작성 화면(/on-01a)으로 이동
   │         └─ 기존 단상 삭제
   │
   ├─ 페이지에서 위로 스와이프
   │    └─ 단상 시트 열림
   │
   ├─ 문장 선택 → “메모”
   │    └─ 인용문+출처를 입력창에 채운 단상 시트 열림
   │         └─ 이후 전송해야 Thought 생성
   │
   └─ 마지막 페이지 → 질문 카드 → 완독 화면
        ├─ 보관하기
        ├─ 나가기
        └─ 다시 읽기 종료
             └─ 답변한 질문 카드마다 Thought 생성 시도
```

### 2.2 진입 경로별 실제 동작

| 진입 경로 | 사용자가 보는 표현 | 즉시 저장 여부 | 실제 결과 |
|---|---|---:|---|
| 우측 하단 FAB | 아이콘만 표시되며 코드상 Memo FAB | 아니오 | `ThoughtsBottomSheet`를 연다 |
| 읽기 페이지에서 위로 스와이프 | 별도 라벨 없음 | 아니오 | 편지 페이지에서만 단상 시트를 연다 |
| 문장 선택 후 “메모” | 메모 | 아니오 | 선택 문장과 `저자, 제목, N면` 출처를 입력창에 채운다 |
| 단상 시트에서 전송 | 단상 / 새 단상 작성하기 | 예 | 글에 연결된 `PRELIMINARY` Thought를 생성한다 |
| 단상 시트에서 기존 카드 선택 | 단상 목록 | 기존 데이터 | 공용 작성 화면에서 해당 Thought를 연다 |
| 질문 카드 답변 후 완독 커밋 | 질문 답변 저장 안내는 없음 | 예, 비동기 시도 | 답변 하나당 `question` 출처 Thought를 생성한다 |

### 2.3 저장 모델

현재 읽기 중 입력은 메모 전용 테이블이나 메모 전용 API에 저장되지 않는다. 공용 `thoughts` 모델을 사용한다.

| 필드 | 읽기 중 단상 | 질문 답변 |
|---|---|---|
| `content` | `# ` 빈 제목 뒤에 인용 블록 형태로 입력값 저장 | `> 질문` + 답변 |
| `createdFrom` | `reading` | `question` |
| `sourceArticleId` | 현재 읽는 글 ID | 현재 읽는 글 ID |
| `status` | `PRELIMINARY` | `PRELIMINARY` |
| 이후 편집 | `/on-01a` 공용 단상 작성 화면 | 기록/단상 흐름에서 재사용 가능 |

DB와 API에서 Thought는 `content`, `createdFrom`, 선택적 `sourceArticleId`, `status`를 가진 공용 엔티티다. `createdFrom`은 `quoted | question | reading | direct`, 상태는 `NORMAL | PRELIMINARY`다. API 명세도 생성 엔드포인트를 “Create a thought (단상)”로 정의한다.

공용 작성 화면은 `PRELIMINARY` Thought를 자동 저장하고, 사용자가 검토 단계로 진행하면 Thought를 `DIVIDING` Article로 승격한다. 따라서 읽기 중 입력은 별도 메모 보관함으로 끝나는 데이터라기보다 **글로 발전 가능한 단상 초안**이다.

### 2.4 저장 후 재열람 경로

- 읽기 화면의 단상 시트는 `sourceArticleId`로 필터링해 현재 글에 연결된 단상만 보여준다.
- 시트의 카드 선택 또는 신규 저장 직후 공용 작성 화면으로 이동한다.
- 공용 기록/단상 UI는 `createdFrom: "reading"`을 “메모”, `createdFrom: "question"`을 “질문”으로 표시한다.
- 동일 데이터가 화면에 따라 “메모”, “단상”, “질문”으로 분류되어 보일 수 있다.

## 3. 운영 중인 구현과 레거시 구현

### 3.1 현재 운영 경로

| 영역 | 역할 | 현재 읽기 화면 연결 |
|---|---|---:|
| `app/read.tsx` | FAB, 위로 스와이프, 문장 인용, 질문 답변 저장 시작 | 사용 중 |
| `ThoughtsBottomSheet` | 글별 단상 목록, 신규 입력, 편집 이동, 삭제 | 사용 중 |
| `app/on-01a.tsx` | Thought 전체 편집, 자동 저장, Article 승격 | 사용 중 |
| Thought API/DB | 공용 단상 저장·조회·수정·삭제·승격 | 사용 중 |
| `lib/analytics.ts` | 문장 선택 후 “메모” 탭 이벤트 | 일부 사용 |

### 3.2 읽기 화면에서 사용되지 않는 메모 전용 계층

코드 검색 기준으로 다음 구현은 현재 앱 코드에서 import되지 않는다. 예외는 테스트가 `MemoWebEditor`의 본문 폭 계약을 문자열로 확인하는 경우뿐이다.

| 구현 | 과거 의도/기능 | 현재 상태 |
|---|---|---|
| `MemoBottomSheet` | 전체 높이 메모 시트, 제목 입력, WebView 편집, 700ms export 기반 자동 저장, 닫기 전 flush | 런타임 미연결 |
| `MemoWebEditor` | 페이지형 WebView 메모, 정적 미리보기, 3D 페이지 플립, 오버플로 자동 분할 | 런타임 미연결 |
| `MemoPageView` | 네이티브 TextInput 기반 페이지 메모와 자체 Markdown 표시 | 런타임 미연결 |
| `memoPages.ts` | Thought `content`에 JSON 문자열 배열로 페이지를 직렬화하고 답변과 합치는 규칙 | 유닛 테스트 외 사용 없음 |

이 레거시는 하나의 구현이 아니라 적어도 다음 세 세대가 겹친 흔적이다.

1. 네이티브 `TextInput` 기반 페이지 메모
2. WebView 기반 페이지 메모와 3D 플립
3. 현재의 가벼운 단상 목록·입력 시트

레거시 코드의 주석은 메모 콘텐츠를 JSON 문자열 배열로 저장하는 계약을 설명하지만, 현재 Thought 스키마에는 페이지 배열 전용 필드가 없고 현재 읽기 흐름도 이 직렬화를 사용하지 않는다. 실제 운영 DB에 이 형식의 과거 데이터가 남아 있는지는 코드만으로 확정할 수 없다.

## 4. 문제 목록과 우선순위

### P0. 저장 성공으로 보이는 순간과 실제 저장 보장이 일치하지 않는다

#### 신규 읽기 중 단상

- 시트는 `createThought.mutateAsync`를 기다린 뒤 작성 화면으로 이동한다.
- 실패 시 경고 로그만 남고 사용자에게 오류·재시도 안내가 없다.
- 사용자는 전송 버튼을 눌렀지만 시트에 그대로 남은 이유나 데이터 보존 여부를 알기 어렵다.

#### 질문 답변

- 보관/나가기/재읽기 종료 커밋 후 `createThought.mutate`를 답변별로 fire-and-forget 한다.
- 실패 시 콘솔 경고만 남으며 화면 이탈은 계속된다.
- 완료 커밋과 답변 저장이 하나의 성공 단위가 아니므로 “읽기 완료는 성공했지만 답변 단상은 사라지는” 부분 성공이 가능하다.
- 답변마다 별도 생성 요청을 보내므로 여러 답변 중 일부만 저장될 수도 있다.

#### DB 제약과 현재 생성 방식의 직접 충돌

`thoughts_writing_source_unique_idx`는 같은 사용자·같은 `sourceArticleId`에 대해 삭제되지 않은 `PRELIMINARY` Thought를 하나만 허용한다.

- 읽기 중 새 단상은 항상 같은 글 ID와 `PRELIMINARY` 상태로 생성된다.
- 질문 답변도 답변마다 같은 글 ID와 `PRELIMINARY` 상태로 생성된다.
- 따라서 이미 해당 글의 활성 초안이 있으면 새 읽기 단상 생성이 고유 제약과 충돌할 수 있다.
- 질문 답변이 여러 개면 첫 생성 이후 나머지 생성은 같은 제약과 충돌할 수 있다.
- 현재 일반 생성 요청은 이 고유 제약을 “기존 초안 재사용” 또는 사용자에게 이해 가능한 충돌 응답으로 바꾸지 않는다.

**영향:** 사용자가 남겼다고 믿는 기록이 사라질 수 있고, 현재 분석만으로 실패 빈도를 알 수 없다.

### P0. 현재 이벤트 이름이 실제 저장을 과대 측정한다

`memo_created_during_reading`은 Thought 생성 성공 시점이 아니라 문장 선택 메뉴에서 “메모”를 누른 시점에 발생한다.

이 이벤트에는 다음이 섞인다.

- 단상 시트를 열기만 하고 닫은 경우
- 인용문을 수정하다 이탈한 경우
- 저장 요청이 실패한 경우
- 실제로 저장하고 작성 화면까지 이동한 경우

따라서 이 수치를 “읽기 중 메모 생성 수”나 저장 전환율의 분자로 사용할 수 없다.

### P1. 사용자 용어와 데이터 모델이 한 흐름 안에서 바뀐다

- 진입 버튼: “메모”
- 열린 시트 제목과 입력 안내: “단상”
- 저장 엔티티/API: Thought(단상)
- 기록 카드 출처 라벨: `reading`은 “메모”, `question`은 “질문”
- 이후 전체 화면: 단상 작성과 Article 승격 흐름

사용자는 짧은 개인 메모를 남긴다고 기대할 수 있지만, 실제로는 글이 될 수 있는 단상 초안을 만든다. 반대로 단상을 쓰고 싶은 사용자는 “메모”를 단순 보조 기능으로 오해할 수 있다.

### P1. 같은 문제를 푸는 편집·페이지 처리 코드가 중복되어 있다

- 네이티브 TextInput 메모 렌더러와 WebView 메모 렌더러가 모두 남아 있다.
- 별도 전체 높이 메모 시트와 현재 단상 시트가 공존한다.
- 페이지 직렬화·오버플로 분할·3D 플립·정적 미리보기·서식 처리 코드가 현재 제품 흐름과 분리된 채 유지된다.
- 공유 본문 폭 테스트가 미사용 `MemoWebEditor`를 아직 계약 대상으로 포함한다.

**영향:** 공용 편집기, 본문 메트릭, WebView, React Native 버전 변경 시 미사용 코드도 함께 수정하거나 테스트 실패 원인을 해석해야 한다.

### P1. 웹/iOS/Android 상호작용 위험이 현재 가치에 비해 크다

현재 단상 시트만으로도 다음 플랫폼 복잡성을 가진다.

- 키보드 show/hide 이벤트가 iOS와 Android에서 다르다.
- 시트 높이는 non-native animation, 슬라이드는 native animation으로 분리된다.
- 닫기 애니메이션 중 투명 컨테이너가 FAB와 페이지 스와이프를 가로채지 않도록 별도 상호작용 잠금이 필요하다.
- 읽기 페이지의 텍스트 선택, 가로 페이지 이동, 위로 스와이프 진입이 서로 충돌하지 않도록 제스처 상태를 조정한다.
- Android 시스템 가장자리 뒤로가기 영역을 별도로 제외한다.

레거시 페이지 메모까지 되살리면 여기에 WebView 포커스, 키보드 유지, 텍스트 선택 핸들, 세로 페이지 플립, 오버플로 자동 분할, 정적 미리보기 동기화가 추가된다. 이는 단순한 “메모 입력창 확장”이 아니다.

### P2. 데이터 계약이 하나로 정리되지 않았다

- 현재 운영 데이터는 일반 Markdown Thought다.
- 레거시 유틸은 같은 `content`를 JSON 문자열 배열로 해석한다.
- 질문 답변은 제목 없이 인용문+답변 형태로 별도 Thought가 된다.
- 읽기 중 단상은 빈 H1과 인용 블록으로 시작한다.

저널 방향을 택할 경우 어떤 형식을 정식 계약으로 삼을지, 기존 Markdown Thought와 레거시 JSON 문자열을 어떻게 판별할지 먼저 정해야 한다.

### P2. 사용 가치를 판단할 측정이 비어 있다

현재 알 수 없는 항목:

- FAB/위로 스와이프/문장 인용 중 어떤 진입이 실제 저장으로 이어지는가
- 시트를 연 사용자 중 몇 명이 저장하는가
- 저장된 읽기 단상을 같은 읽기 세션 또는 이후에 다시 여는가
- 저장된 단상이 Article로 승격되는가
- 단상 작성 때문에 읽기 흐름에서 이탈하는가, 다시 돌아오는가
- 질문 답변 저장 요청은 얼마나 실패하는가
- 읽기 중 단상을 여러 페이지 저널로 만들고 싶다는 실제 수요가 있는가

## 5. 세 가지 해결 방향 비교

### 5.1 공통 평가표

| 기준 | ① 가벼운 읽기 중 단상 유지·개선 | ② 읽기 노트/저널로 재설계 | ③ 읽기 전용 메모 진입점 포기·단계적 제거 |
|---|---|---|---|
| 핵심 가치 | 읽다가 떠오른 생각을 빠르게 단상으로 시작 | 한 글에 대한 지속적이고 구조화된 독서 기록 | 읽기 집중과 제품 단순성 |
| 사용자 약속 | “읽으며 단상을 남기고 나중에 글로 발전” | “이 글 전용 노트를 계속 작성·재열람” | “읽기는 읽기에 집중; 기록은 공용 단상/수집에서” |
| 현재 모델 적합성 | 높음 | 낮음~중간 | 높음 |
| 클라이언트 범위 | 용어, 피드백, 이벤트, 질문 저장 신뢰성 | 정보 구조, 전용 화면, 편집·검색·재열람, 플랫폼 상호작용 전반 | 진입점·제스처·문구 제거, 대체 동선 안내 |
| API·데이터 범위 | 기존 Thought 계약 유지 가능 | 전용 엔티티 또는 명확한 Thought 하위 계약 필요 | 신규 스키마 불필요; 기존 데이터 조회 유지 |
| 구현 위험 | 낮음~중간 | 높음 | 낮음~중간 |
| 기존 데이터 처리 | 그대로 유지 | 읽기 단상을 가져오거나 연결하는 전환 규칙 필요 | 삭제하지 않고 공용 기록에서 계속 접근 |
| 롤백 난이도 | 낮음 | 높음 | 낮음(기능 플래그/단계 제거 시) |
| 검증 비용 | 중간 | 매우 높음 | 낮음~중간 |
| 적합한 관찰 결과 | 저장·재열람·승격이 의미 있게 발생 | 반복 재열람·긴 기록·다중 편집 요구가 확인 | 열기는 많아도 저장/재열람이 낮고 읽기 방해가 큼 |

### 5.2 방향 ① 현재의 가벼운 읽기 중 단상 유지·개선

#### 제품 정의

“메모”를 별도 문서로 만들지 않고, **현재 글에 연결된 단상을 빠르게 시작하는 기능**으로 명시한다.

#### 사용자 가치

- 현재 구현과 학습 비용을 최대한 보존한다.
- 인용에서 시작해 공용 작성 화면에서 긴 글로 발전할 수 있다.
- 글별로 연결된 기존 단상을 읽기 중 다시 찾을 수 있다.

#### 필요한 구현 범위

- “메모”와 “단상” 중 하나를 주 용어로 정하고 진입·시트·기록 라벨을 맞춘다.
- 신규 단상 저장 실패를 사용자에게 보여주고 재시도 가능하게 한다.
- 질문 답변 저장을 완료 커밋과 별도로 추적하고, 부분 실패를 복구 가능하게 한다.
- 열기/입력/저장 성공/저장 실패/작성 화면 이동/재열람 이벤트를 추가한다.
- 현재 연결되지 않은 메모 전용 코드는 데이터 조사 후 별도 작업으로 제거한다.

#### 위험

- 공용 작성 화면으로 즉시 이동하는 동작이 “가벼운 메모” 기대보다 무거울 수 있다.
- 시트가 목록+작성+삭제+편집 이동을 모두 맡아 상호작용 복잡성이 남는다.
- 현재 생성 UI는 여러 항목을 만들 수 있는 것처럼 보이지만 DB는 글당 활성 `PRELIMINARY` Thought 하나만 허용한다. “기존 초안에 이어 쓰기 / 질문 답변 병합 / 여러 항목 허용” 중 하나로 계약을 정해야 한다.

#### 기존 데이터·전환·롤백

- `reading`/`question` Thought를 그대로 유지한다.
- 별도 마이그레이션 없이 문구와 이벤트를 먼저 바꿀 수 있다.
- 변경 후 문제가 생기면 진입 문구·시트 동작을 이전 방식으로 되돌려도 데이터 형식은 변하지 않는다.

#### 선행 조건

- 제품 언어 결정: “메모”를 유지할지 “단상”으로 통일할지
- 신규 저장과 질문 답변 저장의 신뢰성 기준 정의
- 글당 활성 읽기 초안을 하나로 유지할지, 여러 개를 허용할지 결정

### 5.3 방향 ② 읽기 노트/저널로 재설계

#### 제품 정의

읽기 중 단상을 공용 글쓰기의 빠른 입구가 아니라, **글 하나에 계속 축적되는 전용 읽기 노트**로 만든다.

가능한 최소 계약:

- 글당 하나의 저널
- 인용과 개인 생각을 구분해 누적
- 읽기 화면과 기록 화면에서 같은 저널을 재열람
- 저장 상태가 명시적이며 오프라인/재시도 정책이 있음
- 필요할 때 저널 일부 또는 전체를 단상/글로 전환

#### 사용자 가치

- 한 글에 대한 생각을 여러 번 이어 쓸 수 있다.
- 문장 인용, 질문 답변, 자유 기록을 한 맥락에 모을 수 있다.
- “메모”라는 사용자 기대와 데이터 구조가 가까워진다.

#### 필요한 구현 범위

- 전용 저널 엔티티를 만들지 Thought의 명시적 하위 타입으로 둘지 결정한다.
- 글당 하나/여러 개, 블록형/문서형, 제목 필요 여부, 질문 답변 병합 규칙을 정한다.
- 읽기 중 편집, 기록 탭 재열람, 검색, 글로 전환의 정보 구조를 설계한다.
- 자동 저장, 충돌, 오프라인, 실패 복구, 삭제·복원 정책을 마련한다.
- Web/iOS/Android에서 키보드·텍스트 선택·읽기 페이지 제스처를 함께 검증한다.
- 레거시 JSON 페이지 형식을 채택하지 않는다면 변환/보존 판별기를 준비한다.

#### 위험

- 현재 공용 Thought 모델의 단순 연결만으로는 저널의 단일성·누적성·블록 구조를 보장하기 어렵다.
- 과거 페이지형 메모 코드를 되살리는 것이 가장 빠른 길처럼 보여도, 이미 확인된 WebView/플립/포커스/측정 복잡성을 함께 되살린다.
- 긴 기록 수요가 검증되지 않은 상태에서 가장 비싼 방향이다.
- 공용 단상과 저널의 경계가 불명확하면 오히려 기록 위치가 둘로 갈린다.

#### 기존 데이터·전환·롤백

- 기존 `createdFrom: "reading" | "question"` Thought를 먼저 읽기 전용으로 분류해 수량·형식을 조사한다.
- 자동 병합은 원문 손실과 순서 오류 위험이 있으므로 기본값으로 삼지 않는다.
- 안전한 전환은 “기존 단상 가져오기”를 사용자에게 제안하고 원본 Thought는 유지하는 복사/연결 방식이다.
- 새 저널은 기능 플래그 뒤에서 시작하고, 롤백 시 저널을 읽기 전용으로 남겨 내보내기 또는 단상 전환을 제공한다.
- 원본 삭제는 별도 보존 정책과 사용자 확인 없이는 하지 않는다.

#### 선행 조건

- 정성 조사에서 반복 기록·한 글 맥락 유지 요구 확인
- 최소 퍼널에서 저장 후 재열람이 충분히 높음
- 전용 데이터 계약과 충돌/오프라인 정책 합의
- 세 플랫폼 실기기 검증 예산 확보

### 5.4 방향 ③ 읽기 전용 메모 기능 포기·단계적 제거

#### 제품 정의

읽기 화면의 FAB, 위로 스와이프, 문장 선택 “메모” 진입을 단계적으로 종료한다. 공용 단상 작성과 문장 수집은 유지한다.

#### 사용자 가치

- 읽기 중 우발적인 제스처와 UI 방해가 줄어든다.
- “메모인지 단상인지” 모호한 기능을 학습할 필요가 없다.
- 팀은 핵심 읽기와 공용 기록 흐름에 집중할 수 있다.

#### 필요한 구현 범위

- 진입점별 실제 사용량을 먼저 측정한다.
- 대체 동선이 필요하면 “문장 수집” 또는 읽기 종료 후 공용 단상 진입을 안내한다.
- 기능 플래그로 신규 진입만 먼저 숨긴다.
- 기존 글 연결 단상은 기록 화면과 공용 작성 화면에서 계속 접근 가능하게 유지한다.
- 충분한 관찰 기간 후 읽기 화면 전용 상태·제스처·시트 연결을 제거한다.
- 마지막에만 런타임 미사용 메모 코드와 관련 테스트를 정리한다.

#### 위험

- 소수라도 강하게 사용하는 사용자의 핵심 기록 습관을 끊을 수 있다.
- 이벤트가 현재 저장을 과대 측정하므로 기존 수치만 보고 종료하면 판단을 잘못할 수 있다.
- 문장 인용에서 단상으로 발전하는 차별화된 흐름을 잃을 수 있다.

#### 기존 데이터·가역적 종료 절차

1. **측정 단계:** 현재 진입점을 유지한 채 정확한 열기·저장·재열람 이벤트를 수집한다.
2. **신규 진입 중단:** 기능 플래그로 FAB/위로 스와이프/문장 “메모”를 숨긴다. DB와 API는 바꾸지 않는다.
3. **기존 데이터 보존:** `reading`/`question` Thought는 공용 기록 목록과 `/on-01a`에서 계속 열고 편집할 수 있게 한다.
4. **관찰 및 복구 창:** 최소 한 릴리스 주기 동안 불편 신고, 기록 접근 실패, 공용 단상 사용 변화 등을 본다. 필요하면 플래그를 되돌린다.
5. **코드 정리:** 읽기 화면 전용 상태·제스처·시트 연결을 제거한다.
6. **레거시 정리:** 운영 DB에 JSON 페이지형 데이터가 없는지 또는 안전하게 읽을 수 있는지 확인한 뒤 미사용 컴포넌트·유틸·테스트를 별도 변경으로 삭제한다.

**삭제하지 않는 것:** 기존 Thought 행, `createdFrom` 값, `sourceArticleId`, 공용 단상 편집·조회 API. 데이터 삭제나 스키마 축소는 사용 종료와 분리된 별도 결정이다.

#### 선행 조건

- 정확한 퍼널에서 저장·재열람·승격 가치가 낮음
- 사용자 인터뷰에서 대체 동선으로 핵심 요구가 충족됨
- 기존 읽기 단상이 공용 기록에서 누락되지 않는지 검증
- 기능 플래그 또는 즉시 복원 가능한 릴리스 절차 확보

## 6. 결정에 필요한 최소 측정

### 6.1 이벤트 제안

이벤트 이름은 구현 시 프로젝트 분석 규칙에 맞춰 조정할 수 있다. 중요한 것은 아래 단계와 결과를 구분하는 것이다.

| 이벤트 | 발생 시점 | 필수 속성 | 답하려는 질문 |
|---|---|---|---|
| `reading_thought_entry_opened` | 시트가 실제로 열린 뒤 | `article_id`, `entry: fab | swipe_up | quote`, `page`, `platform` | 어떤 진입이 사용되는가 |
| `reading_thought_input_started` | 첫 유효 입력 | `entry`, `has_quote` | 열기 중 몇 번이 작성 의도로 이어지는가 |
| `reading_thought_save_requested` | 전송 탭 | `entry`, `has_quote`, `text_length` | 저장 시도 수는 얼마인가 |
| `reading_thought_save_succeeded` | API 성공 | `thought_id`, `entry`, `duration_ms` | 실제 저장 전환과 지연은 어떤가 |
| `reading_thought_save_failed` | API 실패 | `entry`, `failure_type`, `retryable` | 데이터 손실 위험은 얼마인가 |
| `reading_thought_sheet_closed` | 저장 없이 닫힘 | `entry`, `had_input`, `dwell_ms` | 이탈이 탐색인지 실패인지 |
| `reading_thought_reopened` | 기존 읽기 단상 열기 | `thought_id`, `age_days`, `surface` | 저장 후 재열람 가치가 있는가 |
| `reading_thought_promoted` | 읽기 단상에서 Article 승격 | `thought_id`, `days_since_created` | 단상이 글로 발전하는가 |
| `reading_question_save_batch_finished` | 완료 시 답변 저장 시도 종료 | `answered_count`, `success_count`, `failure_count` | 질문 답변이 신뢰성 있게 남는가 |
| `reading_exit_after_thought` | 단상 작성 화면 이동 후 읽기로 미복귀/복귀 | `returned`, `elapsed_ms` | 기록이 읽기 흐름을 깨는가 |

기존 `memo_created_during_reading`은 즉시 제거하기보다, 일정 기간 새 이벤트와 함께 보내 의미 차이를 확인한 뒤 사용 중단한다. 대시보드에서는 이를 “생성 성공”이 아니라 “인용 메모 진입 탭”으로 재명명해야 한다.

### 6.2 핵심 지표

1. **열기율** = 시트 실제 열기 사용자 / 읽기 활성 사용자
2. **작성 시작률** = 유효 입력 시작 / 시트 열기
3. **저장 전환율** = 저장 성공 / 시트 열기
4. **저장 신뢰도** = 저장 성공 / 저장 요청
5. **7일 재열람률** = 7일 내 다시 열린 읽기 단상 / 저장된 읽기 단상
6. **글 발전률** = 30일 내 Article로 승격된 읽기 단상 / 저장된 읽기 단상
7. **읽기 복귀율** = 작성 화면 이동 후 같은 읽기 세션으로 복귀 / 작성 화면 이동
8. **질문 답변 완전 저장률** = 성공 수가 답변 수와 같은 저장 배치 / 답변 저장 배치

### 6.3 검증 기간과 표본

- 최소 **2주**, 가능하면 주중·주말과 두 번 이상의 읽기 주기를 포함하는 **4주**
- 웹/iOS/Android를 분리해 본다.
- 신규 사용자와 기존 사용자를 분리한다.
- 이벤트 수가 적으면 비율만으로 결론 내리지 말고, 읽기 중 기록을 한 사용자 5~8명과 미사용자 5~8명을 인터뷰한다.
- 저장 실패는 표본이 작아도 허용하지 않는 신뢰성 지표로 취급한다.

### 6.4 사용자 검증 질문

프로토타입 또는 현재 앱을 사용한 직후 행동 중심으로 묻는다.

- “방금 남긴 내용은 어디에 저장됐다고 생각했나요?”
- “이 기록을 다시 찾으려면 어디로 갈 것 같나요?”
- “메모와 단상은 같은 것으로 느껴졌나요, 다른 것으로 느껴졌나요?”
- “작성 화면으로 이동했을 때 읽기가 중단됐다고 느꼈나요?”
- “한 글에 계속 이어 쓰는 노트가 필요한가요, 짧은 생각 하나면 충분한가요?”
- “질문 답변도 같은 노트에 모이길 원하나요, 별도 단상으로 남길 원하나요?”

선호 질문보다 사용 직후의 위치 예측, 재탐색 성공, 실제 작성 길이와 반복 횟수를 우선한다.

## 7. 선택 기준과 조건부 권고

아래 수치는 최초 의사결정을 위한 제안 기준이며, 실제 활성 사용자 규모에 맞춰 조정해야 한다.

### 방향 ①을 선택할 조건

- 저장 전환율이 의미 있게 나타나고(예: 시트 열기의 20% 이상),
- 저장 신뢰도가 99% 이상으로 개선 가능하며,
- 저장된 단상의 7일 재열람 또는 30일 승격이 관찰되고,
- 사용자 다수가 “읽다가 단상을 시작하는 기능”으로 이해한다.

이 경우 페이지형 메모를 되살리지 말고 용어·실패 피드백·이벤트·질문 저장부터 고친다.

### 방향 ②를 선택할 조건

- 같은 글의 기록을 여러 번 다시 열고 수정하는 사용자가 반복적으로 나타나며,
- 기록 길이와 세션 수가 단일 짧은 단상 범위를 자주 넘고,
- 인터뷰에서 글별 맥락 유지·인용 누적·질문 답변 통합 요구가 일관되며,
- 사용자가 공용 단상과 별도의 읽기 저널 위치를 이해할 수 있다.

이 경우 기존 페이지 메모 코드를 바로 복원하지 않는다. 먼저 데이터 계약과 가장 단순한 문서형 저널 프로토타입을 검증한다.

### 방향 ③을 선택할 조건

- 정확한 저장 전환과 7일 재열람이 모두 낮고,
- 기록 후 읽기 복귀율이 낮거나 이탈이 증가하며,
- 인터뷰에서 “문장 수집 + 공용 단상”으로 핵심 요구가 충족되고,
- 기능을 숨긴 실험에서 읽기 완료·만족도가 악화되지 않는다.

이 경우 신규 진입만 먼저 숨기고 기존 Thought 데이터와 편집 경로는 유지한다.

### 지금 시점의 권고

1. **최종 방향은 보류한다.** 현재 이벤트는 생성 성공을 측정하지 못하므로 삭제나 대규모 재설계를 정당화할 근거가 부족하다.
2. **측정 기간의 기본안은 방향 ①이다.** 현재 모델과 가장 잘 맞고, 데이터 마이그레이션 없이 저장 신뢰성과 용어를 검증할 수 있다.
3. **방향 ②는 사용자 수요가 확인될 때만 시작한다.** 레거시 페이지형 WebView를 그대로 되살리는 것은 기본안이 아니다.
4. **방향 ③은 가역적으로 실행한다.** 진입점 숨김과 데이터 삭제를 분리하고, 한 릴리스 이상의 복구 창을 둔다.

## 10. 확인이 더 필요한 항목

코드 분석만으로 결론 내리지 않은 항목:

- 운영 DB에 JSON 문자열 배열 형태의 과거 메모가 실제로 존재하는지
- 글당 하나인 현재 활성 `PRELIMINARY` Thought 제약을 제품 계약으로 유지할지
- 고유 제약 충돌이 실제 사용자에게 어떤 오류로 전달되는지와 현재 발생 빈도
- 질문 답변 Thought 생성 실패율과 부분 성공 빈도
- 사용자가 저장된 읽기 단상을 기록 화면에서 실제로 다시 찾는지
- 페이지형 저널에 대한 실제 수요와 허용 가능한 플랫폼 검증 비용

이 항목은 읽기 전용 진입점이나 레거시 코드를 삭제하기 전에 데이터 조회, 이벤트 측정, 사용자 검증으로 확인해야 한다.
