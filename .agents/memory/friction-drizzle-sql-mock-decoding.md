---
name: Decoding drizzle sql`` templates in unit-test db.execute mocks
description: How to turn a drizzle-orm sql tagged-template object into {text, params} inside a test mock, without a real DB connection or drizzle-orm/pg-core.
---

When production code issues raw parameterized SQL via `db.execute(sql\`...\`)` (chosen over the query-builder because the query needs a conditional atomic upsert/update that the builder expresses awkwardly), a unit-test mock for `db.execute` needs to recover the literal SQL text and the ordered bind parameters from the `sql` object it receives, including when the template nests another `sql` fragment (e.g. `sql.join(...)` for a bulk multi-row `INSERT ... VALUES`).

**Why:** Trying to interpret the query-builder's own condition objects (`eq`, `and`, etc.) inside a mock is fragile and version-dependent. A more robust option — `new PgDialect().sqlToQuery(query)` from `drizzle-orm/pg-core` — works but breaks when instantiated inside `vi.hoisted(...)`: hoisted factories run before the test file's own top-level `import` bindings are initialized, so referencing an imported class there throws `ReferenceError: Cannot access '...' before initialization`. The simplest fix skips the extra import entirely: any `sql` object exposes a `queryChunks` array whose elements are either a `StringChunk` (literal text, `.value` is a string array to join), a nested object whose constructor name is `SQL` (recurse into its own `queryChunks`), or anything else (a bound parameter, in call order). Walking that structure recursively yields the same `{text, params}` pair without needing any drizzle import, so it has no hoisting hazard at all.

**How to apply:** In the mock's `execute` implementation, write a small recursive `queryChunks` walker (constructor-name branch: `"SQL"` → recurse, `"StringChunk"` → collect text, else → collect as a param) and branch behavior on the resulting text (e.g. by SQL keyword prefix) to know which of several raw-SQL operations is being invoked.
