---
name: Multi-step sheet back navigation
description: Pitfall when building a picker with a "choose A, then choose B, with back-to-A" flow, and why it should be one sheet with step-switched body content rather than two composed modal components.
---

Prefer implementing a "choose A, then choose B, with back-to-A" flow as **one sheet/modal component** whose body content switches by local `step` state, rather than composing two separate reusable single-step modal components (e.g. mounting a shared space-picker modal for step 1 and a shared letter-picker sheet for step 2). Composing two full modal components technically works (each can render its own visuals), but it produces a visibly different transition — two separate sheets animating in and out — and duplicates each component's chrome (backdrop, header, close button) instead of one continuous sheet with a back button. When a step needs the same *data and visual style* as an existing single-step picker, copy that rendering (list/row markup, loading/error/empty states) directly into the new component's body instead of mounting the existing component; do not import the existing single-step component itself into a multi-step flow.

**Why:** A user explicitly rejected a version built by composing two modal components (with a `closeOnSelect` opt-out to fix the onClose-conflation bug — see below) and asked for "one sheet from the start" instead of borrowing the other picker's layout as a separate mounted component. Two composed modals also structurally can't share one continuous open/close animation or one `BottomSheet` drag/snap state.

**The onClose-conflation trap this replaces:** if you *do* reuse a shared single-step picker modal as a sub-step (an earlier, since-abandoned approach here), that modal's own tap handler commonly calls both `onSelect(item)` and `onClose()` — correct for a real single-step flow, but wiring the *outer* flow's `onClose` straight into it closes the whole multi-step flow the instant step 1 is chosen, before step 2 can ever show. `onClose` is overloaded between "this modal is done" and "the whole flow is abandoned." This is why composing existing modals for a new step is risky even with a `closeOnSelect` escape hatch — prefer inlining the step's rendering into the new single-sheet component instead.

**How to apply:** Build the multi-step flow as one `BottomSheet` (or equivalent) instance. Keep a local `step` state; render step-specific body content conditionally inside the same sheet body, and reset `step` back to the first step whenever the flow's own `visible` prop turns true so a stale later-step selection never survives a reopen. Use the sheet's `headerLeft` slot (with a matching spacer opposite it to keep the title centered) for a "back to previous step" button — plain `setStep`, no `onClose` involved. Reserve the sheet's own `onClose` (backdrop tap / swipe dismiss) for abandoning the whole flow from any step.

Because this codebase has no component-render test harness (see friction-large-screen-test-convention), verify a fix like this with source-text assertions that check the *specific* wiring: exactly one sheet component is rendered (not two), the reused single-step component is not imported/mounted at all, and step-advancing selection handlers never call the outer `onClose`. A looser assertion (e.g. just "the sheet component is used") will not catch a regression back to the two-modal composition.
